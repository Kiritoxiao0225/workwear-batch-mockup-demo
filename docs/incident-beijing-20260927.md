# 北京 mockfits 故障恢复记录（2026-09-27）

## 已确认的故障原因

服务器重启后，PostgreSQL 启动成了一个新空库，`mockup_app` 不存在，业务 schema 没有表。页面显示密码认证失败，两个 worker 因同一错误退出。

现场运行镜像是 PostgreSQL 17.11，Zeabur 持久卷挂在 `/var/lib/postgresql`，实际数据目录却是被匿名容器卷覆盖的 `/var/lib/postgresql/data`。父目录持久化没有保护到真正的数据目录。官方 PostgreSQL 镜像文档也明确说明了 17 及之前版本这一挂载陷阱：[PGDATA 与卷目录](https://github.com/docker-library/docs/blob/master/postgres/README.md#pgdata)。平台保存的服务规格声明 PostgreSQL 18，而实际运行镜像为 17，卷目录没有适配；模板与运行镜像不一致是这次配置错误的重要线索，未确认具体变更时间和操作者。

这解释的是重启后空库和认证失败。**最初主机为何离线仍未确定**：未取得主机 SSH 和当时系统日志，现有证据不足以判断为内存耗尽、云平台故障或其他原因。

- 恢复 2 个原账号、21 个款式、260 个颜色，图片继续引用现有对象存储。原空库和可用旧备份保留，没有删除旧主机目录。
- WPS 重新读取 636 条来源记录，其中 10 条符合当前生产条件；同步没有改写 WPS 原表。页面 WPS 专用索引已建立。
- 用户的原管理员账号和内部工作区保留。快照时该账号尚无密码，用户通过邮箱首次设密恢复了密码登录；没有重建或替换账号。
- 9 月 22 日备份之后的数据库记录不能声称完整恢复。9 月 25 日文件只是部分清理快照，未作为整库备份盲目回放。

## 防止复发的变更

1. PGDATA 改为持久卷内 `/var/lib/postgresql/pgdata`。启动守卫检查实际挂载、PG 17 版本和系统标识；缺数据时拒绝自动建空库。配置与 TLS 都通过平台回读核实。
2. 恢复基线写入 `recovery-hold.json`，阻止自动识别/续做恢复出的旧需求。手动提交和后续新增需求仍可工作。原快照没有 queued/running 付费任务。
3. main worker 定期将业务一致性快照压缩上传到现有私有 R2，上传携带 Content-MD5 让 R2 核验后落盘，再 HEAD 回读长度和 MD5 ETag；SHA-256 随回执保存，完整下载/恢复已另行演练。间隔 6 小时，专用目录保留 7 天；失败重试和过期健康状态由程序维护。
4. Web 平台探针改为 HTTP `/api/health`，检查数据库及迁移；worker 使用 HTTP `/` 检查心跳，main worker 同时报告备份新鲜度。平台 RUNNING 仍不能替代真实功能检查。

Zeabur 内建自动备份被 API 拒绝，理由是自定义镜像没有被识别为数据库。因此采用项目自身的备份逻辑，没有声称已打开平台自动备份。

## 运维边界

这套保护解决了本次错误卷挂载、空库静默启动和缺少近期异地备份的问题，不等于多机高可用。整个主机离线仍会导致网站暂时不可用；6 小时备份间隔仍存在最近数小时数据损失窗口。进一步查明最初主机离线原因，需要主机 SSH 或云平台当时的系统事件。恢复密码后应妥善保存主机登录方式，避免下次无法检查操作系统日志。

### 云端备份校验修正

北京 worker 上传约 100 MB 备份成功，但整包 GET 读回在 300 秒后超时，4 MB Range GET 也在 20 秒超时；同一对象 HEAD 约 0.94 秒成功。现采用 R2 支持的 Content-MD5 入库校验，加 HEAD 回读长度与单次 PUT 的 ETag；任何不匹配都不记成功、不删除旧备份。完整 SHA 下载与独立恢复验证保留为实际演练证据，不能将 HEAD 表述为完整下载。参考：[R2 S3 API 兼容性](https://developers.cloudflare.com/r2/api/s3/api/)。新增三项回归覆盖正确回读、摘要不符和长度不符。

云端执行修正后的备份函数成功，11:49 生成 99,950,296 字节快照并完成 R2 校验与 HEAD 回读；随后从本机完整下载该云端快照，SHA-256 与云端回执一致。证据：`cloud-backup-verification-v2.json`、`cloud-backup-full-readback.json`。

11:56 最终回读：Web、main worker、external worker 均为 HTTP 200 / ready；两个 worker 镜像与三个补丁源码 SHA 一致。main 定时备份已启用，成功回执时间为 11:49，无错误；外部 worker 不重复执行备份。最终证据：`final-verification-v2.json`。


## 进一步稳定性整改（2026-09-27）

原配置不一致已定位到 9 月 21 日部署记录：20:49 创建 PG18 规格，20:51 将运行镜像换为 PG17，卷与 PGDATA 没有成套调整。原始主机失联原因仍缺内核日志；事前内存最高 91.84%、CPU 到 100%，因此同时增加资源保护。

- 数据库声明与实际镜像统一到同一 PG17.11 镜像摘要，原浮动 `17-alpine` 与新固定镜像的仓库摘要一致；持久卷、业务账号、TLS 配置均保留。增加二进制主版本检查。发布前固定合同检查能够拒绝本次原始错误。
- 定时备份从制作进程中移至独立子进程，512 MB 为 JavaScript 堆限制（不是整个进程 RSS 限制），20 分钟超时。只读一致性快照每批 16 行写入临时文件，再流式压缩、上传；数据库事务不跨越远端上传。保留原 v1 恢复格式和校验规则，不把 HTTP HEAD 冒充完整恢复演练。
- main/external 的并发分别从 20 调整为 6/3，每个轮询最多新领 1 项，RSS 暂停阈值分别为 1280/768 MiB。主机可用内存低于 1024 MiB 或总内存 15% 的较大值时暂停领单；恢复有回滞。已有任务和续租继续，未知付费任务保持不自动重跑。高峰期排队会更保守。
- 制作健康探针和备份新鲜度拆分；备份故障单独在 `/ops/backup` 报告，避免把备份故障扩大为制作后台重启。
- 本轮没有开通付费服务器升级。Zeabur 创建资源告警 API 返回 `Upgrade needed`，平台自动通知未启用，不能把新增健康端点表述为外部告警已经送达。

本次备份与持久化整改不等于多机高可用，仍保留约 6 小时加轮询间隔与备份执行时间的数据窗口；15 分钟 RPO/PITR 和独立数据库主机不在本次已完成范围。资源准入保护是软限制，不冒充整个共享宿主机的硬资源隔离。发布材料在 `output/stability-20260927/`，`private/` 不提交、不输出。

## 2026-09-28 旧登录失效后的自动恢复

- Web 修复提交 `b67fa83`：工作台会话接口返回 401 时自动进入 `/login?reason=session-expired&next=...`，保留原路径、查询参数和锚点；登录页说明使用原账号登录并返回原页面。登录、注册、找回密码页面不再发后台会话检查，避免跳转循环和新 Cookie 被旧检查干扰。
