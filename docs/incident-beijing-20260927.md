# 北京 mockfits 故障恢复记录（2026-09-27）

## 已确认的故障原因

服务器重启后，PostgreSQL 启动成了一个新空库，`mockup_app` 不存在，业务 schema 没有表。页面显示密码认证失败，两个 worker 因同一错误退出。

现场运行镜像是 PostgreSQL 17.11，Zeabur 持久卷挂在 `/var/lib/postgresql`，实际数据目录却是被匿名容器卷覆盖的 `/var/lib/postgresql/data`。父目录持久化没有保护到真正的数据目录。官方 PostgreSQL 镜像文档也明确说明了 17 及之前版本这一挂载陷阱：[PGDATA 与卷目录](https://github.com/docker-library/docs/blob/master/postgres/README.md#pgdata)。平台保存的服务规格声明 PostgreSQL 18，而实际运行镜像为 17，卷目录没有适配；模板与运行镜像不一致是这次配置错误的重要线索，未确认具体变更时间和操作者。

这解释的是重启后空库和认证失败。**最初主机为何离线仍未确定**：未取得主机 SSH 和当时系统日志，现有证据不足以判断为内存耗尽、云平台故障或其他原因。

## 恢复范围

- 用户明确接受无法恢复的业务记录不再追索，优先恢复使用。
- 使用 9 月 22 日 11:38 的完整 PostgreSQL 备份，SHA-256 `1005f697e340b35cca8a09cad50b4fbea276496ff574fd90f25d707b823b5188`。恢复 51 张表，再补迁移 023 到 57 张表。
- 恢复 2 个原账号、21 个款式、260 个颜色，图片继续引用现有对象存储。原空库和可用旧备份保留，没有删除旧主机目录。
- WPS 重新读取 636 条来源记录，其中 10 条符合当前生产条件；同步没有改写 WPS 原表。页面 WPS 专用索引已建立。
- 用户的原管理员账号和内部工作区保留。快照时该账号尚无密码，用户通过邮箱首次设密恢复了密码登录；没有重建或替换账号。
- 9 月 22 日备份之后的数据库记录不能声称完整恢复。9 月 25 日文件只是部分清理快照，未作为整库备份盲目回放。

## 防止复发的变更

1. PGDATA 改为持久卷内 `/var/lib/postgresql/pgdata`。启动守卫检查实际挂载、PG 17 版本和系统标识；缺数据时拒绝自动建空库。配置与 TLS 都通过平台回读核实。
2. 恢复基线写入 `recovery-hold.json`，阻止自动识别/续做恢复出的旧需求。手动提交和后续新增需求仍可工作。原快照没有 queued/running 付费任务。
3. main worker 定期将业务一致性快照压缩上传到现有私有 R2，上传后完整下载核对 SHA。间隔 6 小时，专用目录保留 7 天；失败重试和过期健康状态由程序维护。
4. Web 平台探针改为 HTTP `/api/health`，检查数据库及迁移；worker 使用 HTTP `/` 检查心跳，main worker 同时报告备份新鲜度。平台 RUNNING 仍不能替代真实功能检查。

Zeabur 内建自动备份被 API 拒绝，理由是自定义镜像没有被识别为数据库。因此采用项目自身的备份逻辑，没有声称已打开平台自动备份。

## 验证证据

- 持久性：数据库容器实际重建后，系统标识保持 `7690045641270210599`；57 张表计数和内容指纹一致。启动守卫正确配置通过，错误 PGDATA 被拒绝。

- 异地恢复：从 R2 下载 95,346,114 字节首份备份，核验压缩文件与 payload 两层 SHA，在独立 PostgreSQL 17 恢复，48 张业务表的行数及规范化逐行哈希全部一致。测试库已停止并清理。时间戳比较统一为 UTC，保留微秒。
- 源码：TypeScript 检查、变更范围 ESLint、11 项自动流程回归、shell 语法与实际守卫检查通过。
- Web 和 worker 原生产构建基于 `165ea94e...` 内容指纹，本次只为 worker 增加恢复隔离与备份补丁；Web 没有重建或混入尚未发布的本地产品改动。

完整机器回执位于 `output/incident-beijing-20260927/`，其中 `private/` 保存私密操作材料；不得把私密目录上传 Git。最终部署标签、健康回读和备份回执以该目录的最终验收记录为准。

## 运维边界

这套保护解决了本次错误卷挂载、空库静默启动和缺少近期异地备份的问题，不等于多机高可用。整个主机离线仍会导致网站暂时不可用；6 小时备份间隔仍存在最近数小时数据损失窗口。进一步查明最初主机离线原因，需要主机 SSH 或云平台当时的系统事件。恢复密码后应妥善保存主机登录方式，避免下次无法检查操作系统日志。
